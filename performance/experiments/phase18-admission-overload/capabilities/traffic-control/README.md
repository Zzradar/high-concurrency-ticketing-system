# Phase18 traffic controls (capability evidence, not A/B)

The default policy remains OFF. Local resource quotas apply in all modes. OFF skips the new Redis token decision. OBSERVE runs the same atomic account/event buckets and counts decisions without returning a limiter rejection. ENFORCED/PAUSED use 429 RATE_LIMITED for rate exhaustion; local capacity rejection is 503 SYSTEM_OVERLOADED. Both include bounded retryAfterMs and a ceiling Retry-After of at least one second. Redis failures for new formal work return 503 ADMISSION_UNAVAILABLE; there is no PostgreSQL counter fallback.

Every operation costs one whole token. Redis stores integer milli-tokens, refills from Redis TIME, clamps negative elapsed to zero and elapsed above one hour, commits both buckets atomically, never charges either bucket on rejection, and bounds TTL to one day. Account capacity/rate are 20/10 and event capacity/rate 200/100 per operation in this example config. These are testable input and instance safeguards, not measured production capacity.

Independent quotas are PUBLIC_STATIC_READ, ADMISSION, AVAILABILITY, INVENTORY_WRITE, RECOVERY, FINANCIAL, ADMIN (16 each), and POSTGRES_FALLBACK (2). Admission Redis work has a further immediate four-work limit. No local admission wait queue is accepted beyond those four active jobs. Permits use shared ownership, exception-safe destruction, and once-only completion. Reservation result lookup and Checkout state classification use RECOVERY; genuinely new work transfers to INVENTORY_WRITE after admission/rate checks, releasing the classification permit. Existing idempotent results, RESERVED/SUBMITTING confirmation, reducing/empty selection, cancellation and financial paths do not consume the new-work token buckets. Internal Checkout reservation continuation reuses its outer workflow budget.

Inventory quota failures and internal inventory/Checkout database failures request an event-specific five-second cooldown. Failure callbacks are deliberately conservative: a repository internal failure also pauses new admission even when it is not specifically a timeout. The scheduler publishes cooldowns with Redis TIME and NX/TTL semantics, bounded to scheduler_batch per tick; repeated overload does not extend an already active marker. Existing admitted leases and positions remain. Scheduler metrics distinguish ADMIN_PAUSED, RUNTIME_PAUSED, PREQUEUE and SALES_ENDED. No CPU feedback tuning or inventory truth is stored in Redis.

Drogon's pinned DbClientManager.cc was inspected: non-fast PostgreSQL clients call newPgClient once with connectionNumber; only fast clients multiply the count through per-loop storage. All five configs remain is_fast=false, PostgreSQL 4, existing Redis seat_holds/auth_sessions 2+2, separate traffic_control 2. A deployment budget is 4 times the API/worker process count, plus explicit migration/monitor/operations reserves. This two-API test fixture needs 8 API PostgreSQL connections plus its test psql connections. Production instance count and reserves require separate sizing; max_connections was not increased. Independent permits do not eliminate contention or timeout delays in the unchanged shared PostgreSQL pool. Strict authentication remains before business controllers and retains its existing PostgreSQL checks.

Real OFF saturation sends 32 simultaneous reads while a bounded three-second lock blocks this fixture's session_seats. The gate requires exactly a 16-request Availability high-water, 503 rejections with the correct resource, complete drain to zero, twenty successful follow-ups, and financial/recovery HTTP 200. Process VmHWM/RSS/threads are sampled against the unchanged 1 GiB/256-pid container limits. This is bounded overload evidence for that workload, not a claim of arbitrary sustained load or production SLA.

The frozen baseline/manifest.json and delivery manifest are untouched. These capability logs are separate from OFF before/after measurements. Phase18 remains incomplete until caching, polling, remaining regressions and final frozen-protocol A/B pass. Closed fixture fixes: the recovery-list saturation call needed its required sessionId; the warm status SQL test now respects the account refill without weakening the zero-SQL assertion. Old metric contracts now include explicitly named Phase18 collectors and fixed labels rather than ignoring newly added metrics.
