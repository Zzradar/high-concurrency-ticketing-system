# 高并发票务系统：购票会话与故障恢复方案设计

## 1. 设计目标

本文在已完成的 Phase 3 正式原子预订能力之上，定义 Checkout Session（购票会话）、关键写操作幂等和分层故障恢复的长期架构边界。

目标是：

- 为一次连续购票过程提供稳定的服务端身份；
- 区分购票流程身份与单次写操作身份；
- 在刷新、网络中断、响应丢失和换设备后恢复服务器事实；
- 冻结结果未知的当前会话，同时允许用户知情后进行独立购买；
- 保留 PostgreSQL 作为正式库存与防超卖的最终权威。

本文的购票会话边界已在 Phase 5 落地；精确 Schema、API 和事务编排见
[Phase 5 购票会话落地设计](checkout_session_phase5_design.md)。Redis、消息队列和周期性 CheckoutSession Worker 仍不在当前范围。

## 2. 购票会话

一条购票会话表示：

> 某个用户针对某一个具体场次进行的一轮连续购票过程。

它是整轮流程的稳定业务身份，不等于 Reservation、Order、幂等键或未来后台操作编号。

```text
用户 U1
├─ 购票会话 C1：演唱会场次 S1
└─ 购票会话 C2：篮球比赛场次 S2
```

同一用户可以拥有多个并行、互不替代的购票会话。不能以“该用户已有一个未完成请求”为由全局阻止其他独立购买。

## 3. 创建时机

在第一次真实产生选座/购买意图时创建会话，例如：

```text
用户第一次点击 A01
→ 创建购票会话 C1
→ A01 进入 C1 的本轮选座流程
```

打开活动列表、场次列表或仅浏览座位图不应制造服务端会话。等到最终确认时才创建又不利于未来临时占座、刷新恢复和多流程隔离。

Phase 5 的 `POST /checkout-sessions` 已把创建会话和第一版完整 `seatIds` 合并为一次请求。它不是占座，不修改 SessionSeat 状态。

## 4. 会话并发边界

```text
不同用户
→ 高度并发

同一用户的不同购票会话
→ 可以并发

同一购票会话内相互独立的选座操作
→ 可以受控并发

同一购票会话的关键确认
→ 同一时刻只能有一个执行中的确认

同一个具体座位
→ 最终由 PostgreSQL 正式库存并发控制仲裁
```

串行范围应缩小到真正冲突的会话状态或具体资源。高并发能力来自无关用户、会话和座位之间的并行，而不是允许同一会话同时执行互斥状态迁移。

## 5. 幂等键职责

`Idempotency-Key`（幂等键）只标识购票会话中的一次关键写操作：

```text
购票会话 C1
  ↓
确认操作 K1
  ↓
Reservation R1
  ↓
Order O1
```

网络异常后重试同一确认必须继续使用 `C1 + K1`，不能生成 `C1 + K2`。新键表示新的逻辑写操作，无法替代对原操作结果的解析。

Phase 3 的 Reservation 专用幂等继续有效：`(user_id, idempotency_key)` 唯一约束和原请求一致性判断仍负责 `POST /reservations` 的并发重试仲裁。购票会话不是对该能力的否定或替换。

当支付、取消等多个关键写接口出现后，可以评估通用幂等请求基础设施。概念上它可以记录用户、操作类型、幂等键、请求摘要、执行状态、结果资源、最终结果和时间信息；本阶段不新增表，也不固定字段或状态。

## 6. 三级故障恢复

### 6.1 第一层：按购票会话恢复当前流程

浏览器仍知道 `C1` 时，用它向服务器查询当前流程。服务器可能返回正在选座、正在确认、已确认并关联 Reservation / Order 或其他后续定义状态。

浏览器可以保存会话编号作为快速恢复线索，但服务器状态是最终事实。

### 6.2 第二层：按原幂等键解析结果未知的写操作

如果 `C1` 的确认操作 `K1` 已经发出但客户端不知道结果，必须使用原 `K1` 继续解析同一逻辑操作。服务端可能：

- 返回已经创建的同一 Reservation / Order；
- 在原操作确实未成功时继续执行该操作；
- 在原操作仍执行时报告处理中，未来也可通过专门状态查询机制继续获取结果。

这一层回答“刚才那次关键写操作到底发生了什么”，不能承担整个购票流程身份。

### 6.3 第三层：按用户身份恢复服务器业务数据

当会话编号和幂等键都已丢失时，最终兜底来自用户身份。未来应能查询该用户进行中的购票会话、待支付订单和最近订单。

恢复顺序总结：

```text
浏览器仍知道购票会话
→ 按购票会话恢复

具体写请求结果未知
→ 按原幂等键恢复

浏览器所有本地状态都丢失
→ 按用户身份恢复服务器业务数据
```

## 7. 确认结果未知：冻结会话但不阻塞用户

假设购票会话状态为：

```text
C1
A01 + A02
SUBMITTING（正在确认）
```

则 C1 的座位集合冻结，不能替换其中座位后沿用 C1 再次确认，也不能在 C1 内同时发起第二笔独立正式购买。客户端必须继续恢复或查询 C1 的原确认操作。

默认处理为：

- 成功：C1 关联 `Reservation R1` 和 `Order O1`，进入 O1 并告知上一笔已成功；
- 明确失败：允许回到可重新选座状态，或由用户明确开启新会话；
- 仍在处理：显示“上一笔预订正在确认”，不把普通后续操作解释为另一笔订单。

购票会话完整状态集合已确定为 `SELECTING / SUBMITTING / RESERVED / ABANDONED`。
`SUBMITTING` 持久化服务端生成的活动确认 Key；`RESERVED` 只持久化 `reservation_id`，不存 `order_id`。会话没有短期 `expires_at`。

冻结只作用于 C1，不采用“存在一个 `SUBMITTING` 会话就阻止整个用户”的规则。

## 8. 显式创建第二购票会话

当 C1 仍可能成功时，系统必须明确告知用户这一风险。只有用户明确选择继续，才创建独立购票会话 C2：

```text
用户 U1
├─ C1：演唱会，SUBMITTING
└─ C2：篮球比赛，SELECTING
```

禁止在 C1 超时或响应丢失后静默生成 C2。

如果 C1 后来成功，系统通知用户并显示对应待支付订单，C2 不自动取消。用户可能最终拥有两笔订单，这是用户知情后继续购买的结果。如果 C1 后来失败，通知用户，C2 不受影响。

## 9. Redis 临时占座的未来角色

Phase 7 可以引入与购票会话关联、带 TTL 的 Redis 临时占座，用于点座阶段提前暴露竞争、改善体验和削减正式确认时的无效请求。

概念关系为：

```text
场次座位 S1:A01
→ 临时归属购票会话 C1
→ TTL 到期自动释放
```

Redis 不作为正式防超卖依据。正式确认链路始终为：

```text
购票会话
↓
PostgreSQL 事务
↓
SessionSeat FOR UPDATE
↓
检查正式库存
↓
Reservation
↓
HELD
↓
Order
↓
COMMIT
```

Redis 故障可以让临时占座体验降级，但不能削弱 PostgreSQL 的事务、行锁和约束，也不能导致正式超卖。Redis key 和协调细节留到 Phase 7 确定。

## 10. 异步受理与后台查询的未来角色

Phase 9 只在压测证明同步确认产生大量 HTTP 等待、请求积压或数据库过载时，才评估限流、排队、异步受理和 Polling（轮询查询）。

未来可能出现：

```text
确认 C1
→ HTTP 202
→ 后台操作编号 P1
→ 客户端查询 P1
```

`P1` 只代表一次后台执行中的操作，不等于购票会话编号、幂等键或 Order ID。当前不实现，也不预先选择消息队列或后台执行框架。

## 11. 现有 Phase 3 如何融入长期架构

Phase 3 已完成并验证以下正式能力：固定顺序锁定 `SessionSeat`、`SELECT ... FOR UPDATE`、多座位全部成功或全部失败、Reservation/关联/Order 同事务创建、价格快照、正式 `HELD`、Reservation 专用幂等以及 COMMIT 成功后返回。

长期调用链为：

```text
购票会话
↓
选座
↓
（未来 Redis 临时占座）
↓
确认购票会话
↓
复用现有 Phase 3 ReservationService / 正式 Reservation 事务
↓
Reservation
↓
Order
```

当前 CheckoutSession confirm 入口负责会话状态和恢复语义，正式库存仲裁仍复用 Phase 3 能力。Phase 3 不是临时方案、失败方案或待废弃接口；当前 `POST /reservations` 仍是已实现 API。

## 12. 舍弃方案

以下方案不作为长期架构：

1. 一个用户全局唯一的 `pendingReservationAttempt`；
2. 仅使用 Vue `ref` 恢复业务流程；
3. 仅使用 `localStorage` 或 `sessionStorage` 作为正式状态；
4. 仅使用幂等键承担整个购票流程身份；
5. 因确认超时而静默创建第二会话或第二订单；
6. 以 Redis 临时占座替代 PostgreSQL 正式库存控制。

## 13. 暂缓方案

- 通用幂等请求表：等多个关键写接口出现后评估；
- 主动取消或放弃 `SUBMITTING` 会话：先设计确认与取消的原子竞争；
- 限流、排队、异步受理和后台操作查询：等真实压测证明需要；
- Redis key、临时占座协调细节：Phase 7 设计时确定；
- 消息队列、微服务拆分和具体 Worker 框架：不在当前范围。

## 14. 已确认设计结论

1. 购票会话是用户针对一个具体场次的一轮连续购票过程，可以一人多会话并发。
2. 首次实际资源修改时创建会话，纯浏览不创建。
3. 幂等键标识会话中的一次关键写操作；同一操作重试复用原键。
4. 恢复依次覆盖会话、结果未知的写操作和用户身份三个层级。
5. 结果未知时冻结当前会话并持续解析，不阻塞整个用户。
6. 第二会话必须由用户在知晓旧会话仍可能成功后显式创建。
7. Redis 只做临时占座和体验优化，PostgreSQL 继续负责正式库存正确性。
8. Phase 3 正式预订事务继续保留并被未来确认入口复用。
9. 通用幂等和异步受理均为后续评估项，不是当前实现事实。
