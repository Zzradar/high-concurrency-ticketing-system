# Phase14 Load 内存资格与续测

本轮只改变四个主业务分片的内存配额：由 2147483648 字节改为 3221225472 字节（3 GiB）。全局探针保持 2 GiB，所有 CPU、身份、VU（虚拟用户）、请求、响应解析、断言和正式业务参数保持原状。运行覆盖文件仅含 k6 服务的 `mem_limit`，且只在具有主业务角色和执行分段参数的命令上生效；全局探针和单独背景预热不受影响。正式测量结束后写回同等角色选择的标准配置。

复核旧 Run ID（运行编号）`phase14-formal-u1-20260911T172711Z-f6fa49` 的 Docker Engine（容器引擎）原始 cgroup（资源组）计数与采样后，确认内存工作集按原始 usage 减去 inactive_file（非活跃文件缓存）计算，并以实际容器限额为分母。旧容器已经退出，不能伪造它们已不存在的 cgroup 文件；原始引擎计数、配置与旧采样保留。本轮每秒直接读取新容器对应的 `memory.max`、`memory.current`、`memory.stat`、`memory.events`，并在统一业务释放前核验四主分片 3 GiB、探针 2 GiB。

内存资格只执行一次，保留完整正式 U1 脚本和 10000 主 VU 的初始化，观察原始 U1 前 120 秒（按原节奏从 0 升至 2500）。这覆盖第一档升压，不是 2500 人的稳定平台期，不能声称获得正式容量。到 120 秒结束诊断，原正式 1740 秒窗口不改写。若原 90% 保护先触发，立即结束并判资格失败，不能重跑选样。诊断边界主动停止导致的完整正式计划未交付仍原样记录，不伪装成完整正式通过。

资格要求所有主分片工作内存峰值低于 80%，宿主内存低于 80%，末 30 秒增长不超过 5 个百分点；以末段最初五秒与最后五秒均值差记录趋势，保留原曲线。缺少完整窗口或采样、发生交换/OOM（内存耗尽）/重启/系统请求错误/数据库不变量失败均不通过。原 90% 安全线保持不变。新订单与 Redis 状态完成核验后按旧流程恢复已知基线。

旧冷初始化、故障夹具、G0（负载发生器校准）、25/25 Smoke（冒烟测试）、全量测试和 FD（文件描述符）修复验证仅校验引用及哈希，不重跑。只有短内存资格通过才启动十项核心正式场景，保持冻结计划顺序和停止语义。出现新的内存保护不提高配额、不重复 U1。按本轮提示，从服务启动起最多四小时，在三小时三十分后不再启动新场景，保留三十分钟收尾。
