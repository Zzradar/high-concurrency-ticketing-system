# 高并发票务预订系统产品需求与业务规则

## 1. 文档定位

本文记录高并发具体座位票务系统的产品目标和已经确认的长期业务规则，不替代接口契约、数据库 Schema 或具体阶段技术设计。

文中同时包含当前已经实现的能力和后续演进方向。凡标记为后续或按压测决定的能力，都不能视为当前系统已经支持。

## 2. 项目目标

系统面向活动、演出和赛事等具体座位售票场景，支持用户：

- 浏览活动、场次和座位图；
- 使用账号登录，并在不同浏览器中独立保持登录；
- 选择某个场次中的具体座位；
- 确认正式预订并形成待支付订单；
- 完成支付、取消或等待订单超时；
- 在刷新、网络异常或换设备后恢复服务器上的购票进度与订单。

核心目标是在高并发下保证同一具体场次座位不超卖、多座位预订不出现部分成功，并避免因重试或结果未知而把同一个用户意图重复解释成多笔订单。

## 3. 核心用户流程

长期完整流程为：

```text
活动
  ↓
场次
  ↓
座位图
  ↓
选择座位
  ↓
Checkout Session（购票会话）
  ↓
短期临时占座
  ↓
确认预订
  ↓
待支付订单
  ↓
支付 / 取消 / 超时
```

当前 Phase 1～9 已经完成工程与数据库基础、只读查询、正式原子预订、Reservation
专用幂等、订单查询与超时释放、服务端购票会话、前端恢复、Redis 临时占座，以及
异步支付、取消、超时竞争、自动退款、用户登录和多客户端一致体验。

## 4. 核心业务规则

### 4.0 登录与多客户端

未登录用户可以浏览活动、场次和座位图；真正选座、确认、查看订单、支付或取消需要
登录。同一账号可以在多个浏览器同时登录，每个浏览器拥有独立会话；退出一个浏览器
只结束该客户端会话，不影响其他客户端。

用户可以从“我的订单”查看服务器保存的订单，也可以直接刷新或打开订单 URL。另一
客户端已经执行确认、支付或取消时，本客户端应显示“已有结果”或“正在复用原操作”，
不能误导用户认为该结果由本次点击刚刚产生。当前不提供注册、找回密码和 OAuth。

### 4.1 座位、价格与订单

1. 同一个 `SessionSeat` 不能同时出售给两个用户；PostgreSQL 中的正式库存状态是最终判断依据。
2. 一次多座位预订必须全部成功或全部失败，不能只创建部分座位的订单。
3. 每笔正式预订最多包含 6 个座位，前后端都应校验，后端校验是最终保护。
4. 座位价格和订单总金额以服务端数据库及锁座时价格快照为准，不能相信客户端提交的金额。
5. 正式预订成功后提供 15 分钟支付窗口；正式是否过期以后端数据库时间和订单状态为准。

### 4.2 购票会话

一条购票会话表示某个用户针对某一个具体场次进行的一轮连续购票过程。一个用户可以同时拥有多个彼此独立的购票会话，不采用“一个用户全局最多一个未完成会话”的限制。

在第一次真实产生选座/购买意图时创建购票会话：用户第一次点击座位时，创建请求直接携带第一版完整 `seatIds`。仅浏览活动、场次或座位图不创建会话。这些座位仍是购买意图；Phase 7 会为其申请短期 Redis 临时占座，但不会改变 PostgreSQL 正式库存状态。

Phase 5 已确定状态为 `SELECTING / SUBMITTING / RESERVED / ABANDONED`。`SELECTING` 可以用完整集合替换座位并允许空集合；`SUBMITTING` 冻结座位与服务端确认键；`RESERVED` 关联正式 Reservation；`ABANDONED` 为用户明确放弃的终态。购票会话自身没有短期 `expires_at`。

并发边界为：

- 不同用户可以高度并发；
- 同一用户的不同购票会话可以并发；
- 同一购票会话内相互独立的选座操作可以受控并发；
- 同一购票会话同一时刻只能有一个执行中的关键确认；
- 同一个具体座位最终由正式库存并发控制仲裁。

高并发不要求同一个业务对象的所有状态变化并行。系统只串行化本来就不能同时成功的资源或状态。

### 4.3 确认预订与结果未知

`Idempotency-Key`（幂等键）表示购票会话中的一次关键写操作，不是整个购票流程的身份。同一确认因网络异常重试时必须复用原购票会话和原幂等键，不能静默生成新幂等键把重试变成另一笔购买。

确认结果未知时，系统采用以下规则：

> 冻结当前购票会话并持续解析原确认结果；默认引导用户等待，但不阻塞整个用户。

购票会话处于 `SUBMITTING`（正在确认）期间：

- 当前座位集合冻结，不能换座后继续用同一会话重新确认；
- 不能在同一会话内发起第二笔独立正式购买；
- 默认恢复或查询原确认；
- 不允许系统因超时静默生成第二笔订单。

如果原确认成功，进入其关联订单并明确告知用户；如果明确失败，用户可以重新选座或明确开启新会话；如果仍在处理，页面持续显示结果未定。

用户在被明确告知“上一笔仍可能成功”后，可以主动开始另一个独立购票会话。旧会话继续解析，后来成功时显示其订单但不自动取消新会话；后来失败时也不影响新会话。用户因此可能拥有两笔订单，这是知情后继续购买的结果，不是系统重复创建。

主动放弃正在确认的会话暂缓支持，直到确认与取消之间的原子状态竞争被完整设计。

### 4.4 选座阶段临时占座

Phase 7 已在用户真实创建或修改购票会话时提供短期 Redis 临时占座，让其他用户更早
看到座位正在被选择。默认有效期为 5 分钟；成功修改选座会刷新相关 Hold。第一版
没有 heartbeat，因此仅停留页面不会无限续期。

Hold 过期或 Redis 数据丢失不会删除 CheckoutSession 中保存的购买意图。用户仍可继续
操作或确认，由服务端重新尝试取得临时 Hold；正式库存始终由 PostgreSQL Reservation
和 Order 生命周期保证。Redis 不可用时，购买意图仍可保存，但暂时没有临时占座保护，
正式确认继续由 PostgreSQL 防止超卖。

### 4.5 支付、取消与通知

MVP 的模拟支付在发起后约 2～6 秒完成，约有 1% 概率失败。支付失败且订单仍在期限内
时可以重试；支付处理中仍允许用户取消，二者由服务端对同一订单进行最终仲裁。

15 分钟订单期限表示允许开始支付的截止时间。截止前发起的支付会获得约 10 秒的短暂
处理宽限；这不会延长订单供用户再次发起支付的期限。已经取消或过期的订单不会因
迟到成功而恢复，迟到成功的款项会自动全额退款。

用户可以通过右上角通知中心查看订单创建、支付成功、订单取消、订单过期和自动退款结果；支付
失败则在当前订单页直接反馈。第一版不支持对正常 PAID 订单主动发起退票或退款；
自动退款只处理未被订单接纳的迟到或重复支付成功。

## 5. 故障与恢复体验

恢复采用三级策略，浏览器存储只提供线索，服务器状态才是正式业务事实。

### 5.1 已知购票会话

浏览器仍知道购票会话编号时，按该编号查询服务器，恢复 `SELECTING`、`SUBMITTING`、`RESERVED` 或 `ABANDONED` 的当前事实。`SUBMITTING` 会按服务端保存的确认键与 Phase 3 正式结果对账。

### 5.2 已知结果未知的关键写操作

确认请求已经发出但客户端不知道结果时，使用原购票会话和原幂等键解析同一次操作：返回已成功结果、继续尚未成功的原操作，或明确显示仍在处理中。

### 5.3 本地信息全部丢失

浏览器关闭、本地数据清理或换设备后，用户可以按服务器身份恢复进行中的购票会话、待支付订单和最近订单。浏览器中的 Vue 内存、`localStorage` 或 `sessionStorage` 不能成为唯一恢复来源。

订单详情 URL 可以独立恢复，不要求用户从活动列表按原路径重新进入。生产静态服务器
必须支持 history fallback，确保直接访问前端 route 时仍加载应用入口。

明确不采用以下长期方案：

- 一个用户全局唯一的 `pendingReservationAttempt`；
- 只依赖 Vue `ref`；
- 只依赖浏览器持久化；
- 只用一个幂等键承担整个购票流程身份。

## 6. 当前范围与演进范围

### 6.1 已实现

- C++20 + Drogon + PostgreSQL 工程、Schema 与 Seed；
- 活动、场次和座位只读接口；
- `POST /reservations`；
- PostgreSQL 事务、固定顺序行锁、多座位原子锁座；
- Reservation、座位关联和 Order 同事务创建；
- 价格快照、正式 `HELD` 状态和 Reservation 专用幂等；
- COMMIT 成功后返回结果及相关真实并发验证。
- `GET /orders/{orderId}` 与订单超时释放 Worker；
- 服务端 CheckoutSession 创建、查询、完整座位集替换、确认、放弃与恢复对账。
- Phase 6 前端购票会话恢复、结果未知轮询和独立多会话；
- Phase 7 与 CheckoutSession 关联、默认 5 分钟且可降级的 Redis 临时占座。
- Phase 8 异步模拟支付、取消与超时竞争、PaymentAttempt 查询、迟到成功自动全额退款
  和用户通知中心。
- Phase 9 用户登录、一个账号多个独立浏览器会话、当前会话退出、我的订单、订单深链接、
  已有操作结果提示和跨客户端通知/焦点同步。

### 6.2 后续阶段

- 接入可靠的真实第三方支付渠道及 callback / 主动查单恢复；
- 设计正常 PAID 订单的主动退票与退款能力。

### 6.3 按压测决定

Phase 10 只有在真实压测证明同步确认出现连接等待、请求积压或数据库过载时，才评估限流、排队、异步受理和 Polling（轮询查询）后台操作结果。

Redis 临时占座只用于提前暴露竞争、改善体验和削峰；正式确认仍由 PostgreSQL 事务仲裁。消息队列、WebSocket、多实例和微服务拆分都不是当前必选项。
