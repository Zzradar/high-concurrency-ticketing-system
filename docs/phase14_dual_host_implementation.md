# Phase14 双机正式容量执行方案

本方案的唯一数值来源是 performance/baseline/phase14-targets.json 和现有正式脚本。用户已授权在资格通过后连续执行，任何冻结安全条件失败都停止继续升压。本文件不代表测试已经通过。

## 目标和词语

SUT（被测服务器）承担业务；Load（负载服务器）生成请求。k6（负载测试工具）的 VU（虚拟用户执行单元）不是注册用户总数，也不是每秒请求数。在线用户可以停顿、思考、刷新；到达率表示每秒开始多少次逻辑操作；RPS（每秒 HTTP 请求数）需要把一次操作中的多个请求分别计数。HTTP（超文本传输协议）响应成功还需要业务字段和数据库核验，才能算业务成功。

数据池是 1,000,000 个注册用户、100,000 个有效认证会话，主目标是 10,000 名活跃用户保持 600 秒。十万认证会话不等于十万活跃用户，更不等于十万请求同时到达。

U1（闭合在线模型）维持虚拟用户；系统变慢时请求到达也会变慢。U2（开放等价模型）按冻结的到达率发送，因此用它检查 U1 是否因自动降速掩盖瓶颈。主用户固定分为浏览 60%、临时占座 25%、确认订单 15%；每人最多执行一次购买分支，最多选择 4 个座位，思考 1–10 秒，刷新间隔 30–90 秒。

支付不是上述 15% 全量订单的后续万人支付。它在 U1/U2/J1/O1/L1/L2 中独立启动每秒 2 个模拟支付流程，使用不同用户和座位，模拟渠道延迟 2–6 秒、失败率为 0、每笔必须在 30 秒内到达唯一成功终态。真实 Stripe（外部支付服务）不接收本次负载。

## 拓扑和可信性

SUT 运行 backend（业务后端）、PostgreSQL（关系型数据库）、Redis（内存键值数据库）、两种 exporter（指标导出器）及 Prometheus（指标时序数据库）。Load 运行协调器和 k6，G0（发生器能力校准）期间额外运行 noop（无业务响应服务）。两机使用独立 Compose（容器编排工具）项目，业务只访问 SUT 私网绑定端口；Prometheus 仅绑定 SUT 回环地址，由受限 SSH（加密远程执行协议）在 SUT 本机查询。

运行时私网地址只放在服务器 0600 配置中，证据保存地址哈希和角色。临时 SSH 私钥只在 Load，公钥仅授权 SUT，限制来源为 Load 私网并禁用转发。最终停止专属服务并移除这组临时授权，镜像、卷和历史证据保留。

Load 与 SUT 的主机身份哈希必须不同。主机 /proc（内核资源统计接口）分别读取，不能用 SUT 容器的统计冒充 Load。G0 只向 Load/noop 发压，不重置 SUT、不预热认证、不创建订单、不访问 PostgreSQL。固定 ABBA（关闭详细采样、开启、开启、关闭的预定对照顺序）校准保留相同基础安全观察，比较详细采样的额外影响；P95/P99（95%/99% 样本不超过的延迟）增幅不得超过 5%。任一腿失败结束校准，不挑选最优结果。

初始化也必须满足负载机保护条件。以 U1 首轮为例，除了 10,000 个主 VU，冻结执行器还预分配三个各 4,096 VU 的控制池和 3,496 VU 的支付池，总初始化容量为 25,784 VU；这些探针仍各按每秒 2 次的冻结速率运行，预分配数量不代表同时发送请求。正式双机运行器逐片初始化，小规模 Smoke 并行初始化，利用绑定运行编号和分片编号的就绪信号衔接，整个过程持续按同一间隔采样并执行原安全保护。所有分片必须在原来的共同释放点前就绪（正式提前 30 秒，Smoke 提前 8 秒）；超时即无效，不延后释放点、不减少 VU、不排除启动期 CPU。

U/J/O/H/L/S 还叠加健康、认证和余票控制各2次/秒，共6 RPS；指定支付场景另2流程/秒。正常支付每流程约6+轮询次数个请求，通常额外约16–24 RPS，但实际以原始样本为准。以上估算不把业务冲突计作成功吞吐，也不保证闭合模型必然实现理想速率。开放模型预分配 VU 是承载到达率的执行容量，完整数值由 JSON（结构化文本格式）计划中的 preAllocatedVUs 字段给出，不能把它当作在线人数。

冷页面一次10个读取：认证2、通知2、场次1、活动1、布局1、余票1、可恢复结算列表1、订单列表1。它们保留真实请求依赖和并行关系。浏览分支再读余票；占座分支新增3个写请求；订单分支新增4个请求。异常确认只恢复同一结算，不生成第二次逻辑购买。

## 身份和库存切片

切片采用从0开始、右端不包含的索引，每轮完全恢复后才复用。main（主用户）[0,10000)，calibration（认证校准）[10000,11000)，control（控制探针）[11000,12000)，payment（支付探针）[12000,22000)，expiry（过期夹具）[22000,32000)，background（背景刷新）[32000,42000)，backgroundHold（背景占座）[42000,52000)，backgroundOrder（背景下单）[52000,62000)，login（无既有会话登录账号）[100000,110000)。不同分片共享输入文件，但全局迭代编号划分身份，不重复消费。

座位切片分别为主业务[0,40000)、支付[40000,50000)、过期[50000,60000)、背景占座[60000,70000)、背景订单[70000,80000)、控制[80000,81000)。主业务以每用户4个位置预留，正式低冲突订单只选其中1座；20场次轮转映射。热点场景明确允许按上表共享座位，其余场景不允许交叉使用库存。

Smoke（小规模全链路冒烟）使用targets定义的独立缩小数据和快照，因为每场座位数、身份切片和响应校验与正式数据不同；不把20人数据冒充正式百万用户数据。正式资格同时验证正式数据和独立完整25项Smoke记录。

## 判定及证据

P50（中位数）、P95、P99 均从所有分片原始点重新计算，不平均分片百分位。分别按场景、步骤、结果类别统计：业务成功、预期业务冲突、受控容量拒绝、系统错误、非预期契约结果。稳定容量要求系统错误、非预期结果、容量拒绝均为0；低冲突场景还要求冲突为0。1%是紧急停止线，不是允许1%错误的通过线。

| 操作 | P95上限 | P99上限 |
|---|---:|---:|
| 健康、身份 | 500毫秒 | 1000毫秒 |
| 页面 | 1500毫秒 | 3000毫秒 |
| 余票 | 800毫秒 | 1500毫秒 |
| 占座、调整、确认 | 1500毫秒 | 3000毫秒 |
| 不含思考时间的旅程 | 4000毫秒 | 8000毫秒 |
| 登录受控繁忙拒绝 | 1000毫秒 | 2000毫秒 |

每个开放场景 planned（计划数）=started（实际开始数）=completed（完成数），dropped iterations（未能按计划启动的迭代）=0，interrupted（中断数）=0。每个步骤的开始数必须等于五类结果总和。请求成功率、业务冲突率、容量拒绝率分别用相应计数除以实际开始数；实际请求吞吐由 HTTP 原始请求计数和真实时间计算，旅程吞吐另外报告。

主机证据包括两机CPU使用、steal（虚拟机被宿主抢占时间）、iowait（输入输出等待）、可用内存、交换计数、接口收发/丢弃/错误、磁盘空间和inode（文件系统索引节点）、文件描述符；容器记录CPU配额使用率、内存占比、健康、重启和OOM（内存耗尽终止）。Load CPU持续10秒达到80%或内存达到90%使测量无效，不能据此判定后端容量。

PostgreSQL保存运行前后事务、连接、语句执行累计时间、锁等待、阻塞者、输入输出和预写日志增量。只计入目标应用的活动等待，空闲ClientRead（等待客户端下一条命令）不算锁瓶颈。统计重置、实例重启、语句淘汰使相应增量无效；慢语句采用聚合执行统计和最大等待关联诊断，不能声称已记录每条SQL正文。Redis INFO（服务统计）及导出器提供命中、连接、命令延迟、内存与网络指标，应用端另记录超时和在途量。

数据库全库不变量与每轮范围对账一起验证：不能超卖、出现重复有效所有者、订单/预订/座位状态不一致、身份混用、部分提交或数量不守恒。支付检查唯一被接纳尝试及订单已支付、预订已确认、座位已售；热点冲突需要精确赢家数量，不能用超时代替冲突。

只有有效测量超过业务阈值才是“有效失败”，它可用于报告容量边界。Load饱和、时钟超100毫秒、连续采样缺失、数据或快照指纹不符属于“测量无效”。修复工具必须结束当前批次，测试、提交、push（正常上传提交）并重新同步，从资格重新开始，使用新编号且不覆盖失败。Smoke的capacity（容量判定）和formal_recovery（正式恢复判定）始终不适用。

## 串行顺序、恢复和安全停止

顺序为U1两轮→U2两轮→J1的60/30/10秒→O1的60/30/10秒→E1→H1两路径各两轮→H2的10/20场次→H3两路径→L1对照/登录→L2对照/登录→S1。先低到达率再缩短窗口，便于定位首次失稳。U1/U2任一必需轮未通过不继续；J/O首次不稳定不进入更短窗口；L1背景保护、受控拒绝或恢复失败不执行L2。当前工具不会自动重跑同档挑选最优值；后续复验必须有根因说明并新建记录。

每轮先验证资格仍匹配，再停止专属应用客户端，恢复已校验快照，核对所有表指纹，清空并验证专属Redis为0，再启动并检查健康。不同场景不叠加。业务停止后一般观察300秒；队列在60秒内降到0并连续保持30秒，在途量连续30秒不超过空闲最大值+2，数据库连续30秒无锁/阻塞/闲置事务。恢复控制请求60秒至少100样本，P95同时满足绝对阈值和基线1.5倍；内存峰值低于85%，末60秒相对前60秒均值增长不超过限制的1%。

E1只是现状刻画。最长观察后仍存在合法待回收订单时，报告剩余量、最老年龄和已处理记录正确性；不因没有在60秒排空而伪造失败或通过。配置的60秒排空目标是未来优化目标。

所有安全触发都先停止当前Load生成器，再结束当前批次并保留SUT现场；不会自动进入下一场景。包括超卖/身份/状态异常、核心服务不健康/重启/OOM、持续交换、磁盘不足、文件描述符或网络异常、最老事务等待>3秒、事务等待者>100持续10秒、HTTP在途>100且10秒无完成、非豁免队列≥90%持续10秒。错误停止窗口为10秒，样本≥100时连续两窗错误比例>1%，小样本任一窗≥3错误；登录密码队列受控饱和不单独触发，但其他保护全部保留。

## 时长、执行入口和交付

冻结24项正式业务窗口的最长合计为 **10440秒（2.900小时）**；加释放等待、恢复和执行器宽限的计划上界为 **20813秒（5.781小时）**。此外还需数据生成、每轮恢复、认证校准/预热、登录背景页面初始化及归集耗时，最终报告采用实测时长；费用按用户要求不统计。安全门禁失败时后续场景不执行。
